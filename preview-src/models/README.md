# preview-src/models — 3D models to import into the preview project

Eight `.glb` files for the previewer's object list. They exist because the built-in
3D Shape only offers flat-faced solids: nothing currently in the list has a curved
normal, a UV seam or a pole, so a whole class of shader can't be looked at.

| File | Verts | Tris | What it is for |
|---|---:|---:|---|
| `sphere.glb` | 1225 | 2304 | Every normal direction at once, textbook equirectangular UV |
| `torus.glb` | 2145 | 4096 | Convex *and* concave curvature, plus a hole |
| `cylinder.glb` | 198 | 192 | Flat caps meeting a curved wall — UV seams and hard normal edges |
| `cone.glb` | 148 | 96 | A single pole where every UV converges |
| `capsule.glb` | 1274 | 2400 | Curved everywhere, no pole, no cap seam — the control case |
| `torus-knot.glb` | 6425 | 12288 | Self-occluding, high curvature variation |
| `suzanne.glb` | 11808 | 3936 | Recognisable silhouette; orientation is obvious at a glance |
| `teapot.glb` | 5408 | 9144 | The one everyone knows; non-manifold rim, saddle at the spout |

Every file is **one mesh**, sized to a unit cube centred on the origin, with normals,
a full UV set, and a material carrying the grid texture below.

## Changing the texture

**`grid.png` in this folder is the texture.** It is only written when missing, so a
hand-edited one is never clobbered — delete it and re-run to get the default back.
The default comes from `default_grid_png()` in `glb.py`.

```bash
python3 preview-src/models/apply-grid.py      # same size:      no re-import needed
python3 preview-src/models/build-models.py    # always, so the .glb files match
python3 preview-src/models/fetch-models.py
```

Once the models are imported, that texture exists in three places: the `.glb` here,
the project's copy in `preview-src/images/<name>-diffuse-000.png`, and the exported
sheet in `preview/images/<name>-sheet0.webp`. `apply-grid.py` rewrites the last two.

**Same pixel size → no import or export.** The exported `3dmodels/<name>.zip` stores
each texture's sprite-sheet *rectangle*, and the project's model data its width and
height; neither holds pixel data or a hash, so same-size pixels swap underneath them
cleanly. Construct regenerates both from the same PNG next time it exports, so
nothing drifts.

**Different size → re-import and re-export.** Those rectangles would be wrong and the
UVs would skew. `apply-grid.py` checks and refuses rather than doing it anyway.

### The catch: a save from Construct undoes it

`apply-grid.py` writes the texture the editor already holds a copy of. **Any save or
export from a Construct session that had the project open beforehand writes that
copy back**, reverting `preview-src/images/*-diffuse-000.png` *and* re-baking the
export's sheets from it — silently, exactly the way a re-export ships a stale
`scripts/main.js`. It has happened once already.

So:

- Run `apply-grid.py` **after** any export, not before, and re-run it if you export
  again.
- To make a new texture permanent, **re-import the `.glb` files** — they carry it, so
  the editor's own copy gets updated and no script is needed afterwards.

Treat `apply-grid.py` as the shortcut that avoids a round trip, not as the thing that
makes the change stick.

It needs Pillow (`pip install pillow`); the two build scripts stay dependency-free
because they run on every model change rather than once in a while.

## Why a texture at all is not optional

It is there for a structural reason as well as a visual one. C3 fixes at **import**
time whether a mesh samples a texture at all, and `AnimatedMesh.DrawMesh` then gates
every draw on it:

```js
a && "texture" === i.GetContentType() ? …SetTexture(a)… : …colour fill…
```

A model imported without a material is stuck on the colour-fill branch permanently.
`I3DModelInstance.loadTextureFromURL` still returns `true` on such a mesh — it
really does replace the `ImageInfo` — but nothing ever samples it. So the baked grid
is what makes the previewer's **Model Texture** control work at all.

**A model added here without a texture will silently ignore that control.** The
writer in `glb.py` bakes one into every file, so this only bites a model imported
from elsewhere.

What C3 cannot invent either way is a UV map, which is why every model here has one.
`loadTextureFromURL` is also per-mesh — the other reason each model is a single mesh.

## Regenerating

```bash
python3 preview-src/models/build-models.py   # the six procedural ones, offline
python3 preview-src/models/fetch-models.py   # suzanne + teapot, needs network
```

The `.glb` files are committed rather than generated at build time, because
`fetch-models.py` depends on files in other people's repositories.

## Importing

Adding a 3D Model object type is a **project structure** change, so it needs a
re-export from the Construct editor — see `preview-src/README.md`. In outline:

1. Import each `.glb` into the project's 3D models, replacing any existing one of
   the same name.
2. Add one `Model3D` object type named `model` to the layout, on the same layer as
   `shape3d`, at the same position and size (120, 120, 100³), and **add the
   Placeholder effect to it** — the previewer's shader goes through that effect, the
   same as on `Piggy` and `shape3d`.
3. Re-export and replace `preview/` wholesale, then copy
   `preview-src/scripts/main.js` over `preview/scripts/project/main.js` — the export
   ships whatever copy of the script the editor had in memory, which is often stale.

The `PREVIEW_MODELS` list in `preview-settings.js` and `MODEL_OBJECTS` in the preview
script must both name any model added or removed — `tests/31` asserts they agree.

## Verification

`write_glb` refuses to emit a model whose triangles wind against their own normals
(`assert_outward_winding`). That check exists because the first version of these
models was inverted on all six procedural shapes, and C3 culled every face.

**Do not try to eyeball winding in a viewer.** Render a closed surface with backface
culling and reversed winding and you see the *inside of the far half* — which still
looks like a solid object. That is exactly how the bug got shipped. Measure it: the
signed volume of a correctly wound closed mesh is positive, and that test depends
only on winding and geometry, not on the normals the file claims.

Output is also parsed with the exact three.js build Construct's importer uses
(`r496/3rdparty/threejs/build/three-js-subset.umd.min.js`): all eight load as a
single mesh with normals, UVs in 0..1 and a base-colour map.
